Babylon.js / procedural vegetables

3Dの野菜は、
数式から育つ。

このサイトで扱う18本のプログラムは、3Dモデルも写真も1枚も読み込みません。 点の座標を計算で並べ、模様をその場で描き、光り方を数値で決める。 絵を描く技術ではなく、形を組み立てる技術です。中学・高校の数学で追えるところから順に見ていきます。

01CONFIG

「作る」と「読み込む」はどう違うのか

procedural generation — 手続き的生成

ゲームや映画の3Dは、ふつう誰かが専用ソフトで作ったモデルファイルを読み込んで表示します。 ファイルの中には「頂点1番は(3.2, 1.1, 0.4)」といった座標が何万個も保存されていて、 プログラムはそれを並べて画面に出すだけです。

このプロジェクトは逆のことをしています。ファイルを読まず、 プログラムを実行した瞬間に座標を計算で作る。これを手続き的生成（プロシージャル生成）と呼びます。 野菜のような自然物と相性がよく、いいことが3つあります。

  • 1個も同じにならない — 数値を少し揺らすだけで、形の違う個体がいくらでも出てきます。実物のきゅうりが1本ずつ違うのと同じです。
  • あとから変えられる — 「もう少し太く」がスライダー1本で通ります。モデルファイルなら作り直しです。
  • 軽い — 18本ぜんぶ合わせても、写真1枚より小さいテキストです。

その代わり、形を言葉ではなく数式で説明できないと作れません。 「トマトってどんな形?」に「肩がへこんでいて、縦に浅い筋が6本あって、上から見ると少しつぶれた丸」と 答えられるかどうかが勝負になります。だからこのプロジェクトのコードは、コメントの半分が 野菜の観察記録です。

18本すべてが同じ9層でできている

トマトもシイタケも玉ねぎも、ファイルの構造はまったく同じです。上から順に読めば、 どの野菜でも同じ場所に同じ役割のコードがあります。このサイトの章立ても、この層に対応させてあります。

読む順番のおすすめ。 最初の1本はニンジン.jsがいちばん素直です（円錐に溝を彫るだけ）。 次にキュウリ.js、慣れたらトマト.js。 シイタケ.jsとトウモロコシ.jsは構造が複雑なので後回しでかまいません。
02Rng

同じ種からは、同じ野菜が生える

seeded pseudo random — シード付き擬似乱数

野菜を1個ずつ違う形にするには乱数が要ります。でも Math.random() は使いません。 理由は単純で、やり直しがきかないからです。 「さっき出たあのジャガイモ、いい形だったな」と思っても、二度と同じものは出てきません。 バグを見つけても、同じ状況を再現できません。

そこでシード（種）付きの乱数を自分で書きます。整数をひとつ渡すと、 そこから決まりきった順番で数字が出てくる仕組みです。同じシードなら何度でも同じ列が出ます。 「ランダムに見えるけれど、実は完全に予測できる」——だから擬似（ぎじ）乱数と言います。

>>> や ^ は数字を2進数として混ぜる演算です。 桁をずらして重ねて、掛けて、また混ぜる。カードをシャッフルするのに近い操作で、 「規則性はあるのに人間には読めない」状態を作っています。 0x6D2B79F5 のような数は、混ざり方がよくなるように選ばれた定数です。

実験 — 種をまいてみる

同じ番号を入れれば、何度でもまったく同じ5本が生えます。

つまずきポイント

乱数の使い道は「バラバラにする」ことではなく「ありそうなばらつきを作る」ことです。 太さを完全にランダムにすると、実物には存在しない極端な個体が混ざります。 だからコードでは gauss()（正規分布）を多用します。 平均のまわりに集まり、たまに少し外れる——実物の野菜の分布はこの形です。

03Noise

でこぼこを、なめらかな乱数で作る

value noise & fBm — 値ノイズとフラクタルノイズ

乱数をそのまま並べると砂嵐になります。となりのピクセルと何の関係もない値が出るからです。 でも自然の模様は違います。じゃがいもの皮のムラも、すいかの縞も、 近いところは似ていて、遠いところは違う。この性質を作るのがノイズです。

作り方は3行で言える

  1. 方眼紙の交点にだけ乱数を置く（格子点）
  2. マスの中の点は、まわり4つの値をなめらかに混ぜて決める
  3. マス目を細かくしたものを重ねる（オクターブ）

2番目の「なめらかに混ぜる」に t*t*(3-2*t) という式が出てきます。 これは smoothstep と呼ばれる関数で、0から1へ移るときに端で速度が0になります。 ただの直線で混ぜるとマスの境目に折れ線が見えてしまうので、この一手間が要ります。

3番目の重ね合わせが効きます。大きなうねりの上に半分の大きさを半分の強さで、 その上にさらに半分を——と重ねると、遠目には大きなムラ、近づくと細かいざらつきという 自然物そっくりの模様になります。この重ね方をfBm（フラクタルブラウン運動）と言い、 コードでは fbm3() や fbm2u() という名前で出てきます。

実験 — ノイズを重ねる

回数を1のままにすると、ぼんやりした雲にしかなりません。3〜4に上げた瞬間に「素材」に見えます。

つまずきポイント

野菜の表面を1周する模様は、一周してぴったりつながらないと縫い目が出ます。 そのためコードのノイズには「周期版」があります（v2u() の px 引数）。 格子の番号を x % px で折り返して、右端の乱数と左端の乱数を同じにする、という仕掛けです。

04Profile

横顔を1本描けば、立体になる

profile & sweep — プロファイルと掃引

ここがこのプロジェクトの中心です。野菜の形は、たった1本の折れ線から作られています。 縦軸に高さ y、横軸に半径 r をとった横顔（プロファイル）。 それを軸のまわりに1周ぐるっと回すと、立体ができます。ろくろで茶碗をひくのと同じ理屈で、 数学では回転体と言います。

具体的には、高さを何十段かに分け、それぞれの高さで半径 r の円（リング）を作り、 リングどうしを四角形でつないでいきます。これを掃引（sweep）と呼びます。

実験 — 横顔を動かすと、立体が変わる

● をドラッグしてください。左半分だけ描けば、右は自動で対称になります。

でこぼこのスライダーを動かすと、半径 r にノイズを足していることがわかります。 これがコードでいう「稜（りょう）」「イボ」「輪紋」の正体です。 きゅうりの浅い10本の筋も、ゴーヤーの大きな瘤も、 r を角度と高さの関数で少し増減させているだけです。

つまずきポイント

トマトやピーマンのように肩が折り返す形は、半径 r だけでは作れません。 「同じ高さに r が2つある」からです。だからコードのプロファイルは (r, y) の2列のテーブルで持っています。 ピーマン.js のコメントに「これが無いと肩が折り返せず、ヘタのくぼみが作れない」と書かれているのはこの話です。

05Mesh

三角形の向きと、面の傾き

winding order & normals — 巻き順と法線

3Dの立体は、突き詰めると点の座標と点を三角形に結ぶ番号表の2つです。 Babylon.js では前者が positions、後者が indices。 さらに normals（法線）と uvs を足して VertexData に詰めれば、 それがもうメッシュになります。

三角形には表と裏がある

三角形の3点を、表から見て反時計回りに並べると表向き、逆に並べると裏向きになります。 これを巻き順（winding order）と言います。 GPUは処理を減らすため、裏向きの面を初めから描きません（背面カリング）。 だから巻き順を間違えると、立体が消えたり内側が見えたりします。

コードの finalize() は、これを自動で直します。やり方が上手いので見てください。 代表の頂点をひとつ選び、その法線と「中心からその頂点へ向かうベクトル」の 内積を取る。内積が負なら法線が内側を向いている＝巻き順が逆、と判定して、 三角形の2番目と3番目の番号を入れ替えます。

法線をならすと、なめらかになる

法線は「その面がどっちを向いているか」を表す矢印で、明るさはこれで決まります。 面ごとに1本ずつ持つとカクカクした多面体に見え（フラットシェーディング）、 頂点ごとにまわりの面の平均を持たせるとなめらかに見えます（スムーズシェーディング）。 同じ形なのに、法線の作り方だけで見た目が変わります。

実験 — 向きを壊してみる

「巻き順を逆」＋「裏面を描かない」で、トマトが消えます。3Dで最初に必ず出会うバグです。

つまずきポイント

1周してつながる部分（u=0 と u=1）は、UVのために同じ場所に頂点が2つあります。 放っておくと2つの法線がわずかに違い、そこだけ縦の線が入って見えます。 weldNormals() は座標を8192倍して丸めた値をキーに同じ位置の頂点を集め、 法線を平均して揃えます。これで縫い目が消えます。

06TextureLab

模様も、その場で描く

UV mapping & procedural textures

立体に模様を貼るには、立体のどこが画像のどこかという対応表が要ります。 それが uvs です。掃引のコードで u = j/(M-1)、v = i/(N-1) と 入れていたあれです。u が「一周まわる方向」、v が「下から上」。 地球儀の経度・緯度だと思えばだいたい合っています。

このプロジェクトは画像ファイルを持たないので、模様も <canvas> に 1ピクセルずつ計算で書き込んでテクスチャにします。担当が TextureLab です。 しかも1枚ではなく、同じ「高さの地図」から3枚を作って辻褄を合わせます。

名前役割中身
albedo色そのもの赤・緑・茶などの下地の色
ORM光り方R=陰り / G=粗さ / B=金属っぽさ を1枚に詰めたもの
normal細かい凹凸面の傾きのずれをRGBで記録したもの

normal（法線マップ）が面白いところです。実際には形を変えず、 光の当たり方だけを嘘つくことで、細かいシワやイボがあるように見せます。 三角形を増やさずにディテールが出るので、非常に安上がりです。 作り方は、白黒の高さの地図から、となりのピクセルとの差（傾き）を計算して色にするだけです。

実験 — 模様を描いて、貼る

縞が上下の極（へた側とお尻）で1点に集まります。u を周方向にとった結果、勝手にそうなります。

つまずきポイント

法線マップを自分で焼くとき、上下方向の符号を間違えると 凹みが膨らみに見えます。Babylon.js の座標系では (下のピクセル - 上のピクセル) が正解で、逆にすると OpenGL系の規約になってしまい、横方向は正しいのに縦方向だけ反転した 「ねじれた法線」ができます。キュウリ.js・ゴーヤ.js・サツマイモ.js の 修正履歴に、全部この話が出てきます。

07PBR

「濡れている」「粉をふいている」を数値で言う

physically based rendering — 物理ベースの質感

形と模様が合っていても、光り方を外すとプラスチックの飾りになります。 コードのコメントに何度も出てくる警告です。 いまの3Dは、材質を「現実の光の振る舞い」に沿った少数の数値で表します。これがPBRです。

  • roughness（粗さ） — 0で鏡、1で紙。ハイライトの広がりが変わります。いちばん効く数値。
  • metallic（金属っぽさ） — 野菜はぜんぶ0。
  • clearCoat（透明な上塗り） — 車のワックスのような層。なす・きゅうり・りんごの照りはこれ。
  • sheen（布のような照り） — 産毛のある表面が縁で柔らかく光る。オクラで使用。
  • subSurface（内部散乱） — 光が中に入って散って出てくる。トウモロコシの粒や玉ねぎの薄皮。
  • anisotropy（異方性） — 繊維の方向にハイライトが伸びる。玉ねぎの外皮。

野菜ごとにどれを使うかが、そのまま「その野菜らしさ」になります。 なすとオクラは、どちらも同じような緑〜紫の細長い実なのに、 片方はクリアコート主体、片方はシーン主体。ここを取り違えると別物になります。

実験 — 同じ形を、別の野菜に見せる

粗さを0.05まで下げると、途端に「野菜」から「置物」になります。

つまずきポイント

クリアコートの強さと粗さは、テクスチャの値と掛け算されます。 リンゴ.js の修正履歴に、roughness 0.26 × ORMのG(0.2〜0.6) で 実効0.05まで下がってしまい、周りの建物が映り込んで 「ガラスのリンゴ」になっていた、という記録が残っています。 数値を単体で見ず、掛かった後の値を見ること。

08Havok

盛り付けは、手で置かない

physics engine — 物理エンジンで自然に積む

ざるに野菜を8本盛る。座標を手で決めると、どうしても「並べました」という絵になります。 重なり方に嘘があるからです。そこで物理エンジンに落としてもらう。 重力と摩擦と反発だけ与えて、あとは転がるに任せます。Babylon.js では Havok を使います。

ただし、全部いっぺんに出すと弾け飛びます。生成した瞬間、 野菜どうしが互いにめり込んだ状態から始まるので、そのぶんの反発力が一気に解放されるからです。 コードは0.16秒おきに1本ずつ、山の頂点のすぐ上から落としています。

実験 — 1個ずつ落とす／全部いっぺんに出す

反発を0.5まで上げると、ざるから飛び出します。実物の野菜は跳ねません。

つまずきポイント

物理エンジンはメートル単位で作られています。 このプロジェクトはcm単位なので、そのまま実際の重力 981 を入れると、 1ステップあたりのめり込みが許容量を超えて押し戻され続け、野菜がプルプル震えます。 コードでは重力を 480 まで落として回避しています。 「正しい物理」より「破綻しない物理」を採る、という判断です。
